## 00:00–02:00. Что такое конвейер поставки

Представьте команду, где разработчики сохраняют код и вручную передают архив администратору. На тестовом стенде установлена одна версия Python, на рабочем сервере другая, а сборка выполняется с новой случайно скачанной зависимостью. Невозможно уверенно ответить, какой исходный код работает у клиента. Для решения таких проблем применяется сборочный конвейер: заранее описанная последовательность операций от фиксации изменения в Git до создания проверенного артефакта и его доставки. Не всякий конвейер обязательно развёртывает программу в производство. Его контракт определяет, когда запускаться, с какими правами, какие входы доверенны, где хранить отчёты и при каких условиях остановиться. Хороший конвейер должен быть понятен и воспроизводим другим инженером.

## 02:00–04:00. Continuous Integration

CI означает Continuous Integration — непрерывную интеграцию. Вместо длительной разработки в обособленных ветках команда регулярно объединяет изменения и запускает автоматические проверки. Типичный путь: Git commit, checkout репозитория, подготовка среды, установка закреплённых зависимостей, статический анализ, сборка, unit и integration tests, формирование артефактов. Главная идея: ошибки несовместимости и регрессии выявляются рано. Но красный pipeline не всегда означает уязвимость, а зелёный — не означает отсутствие ошибок. Проверки отражают только заданные условия. Проверка качества требует осмысленных тестовых сценариев и регулярного пересмотра их покрытия.

## 04:00–06:30. Continuous Delivery и Continuous Deployment

У аббревиатуры CD есть два распространённых значения. Continuous Delivery означает, что результат процесса готов к поставке и может быть выпущен по решению человека или установленной процедуре. Continuous Deployment означает автоматическое развёртывание каждого изменения, которое успешно прошло предусмотренные проверки. На собеседовании нельзя смешивать их. Допустим, медицинская система требует отдельного согласования выпуска. Тогда автоматическая сборка и тестирование могут сосуществовать с ручным разрешением production deployment. В FATHER S6 предусматривает подтверждение соответствующими ответственными лицами. В учебной песочнице автоматическое развёртывание может быть допустимо — при этом оно не доказывает готовность продукта к промышленному использованию.

## 06:30–09:00. Почему требуются одинаковые условия

В видеолекции CyberED отдельно показаны требования к одинаковым стендам и связь с Infrastructure as Code. Рассмотрим пример: Python-программа проходит тесты на ноутбуке, но падает в контейнере. Причина может быть в версии библиотеки, архитектуре процессора, системном пакете, переменных окружения или настройках доступа. Для снижения неопределённости используются lockfile, закреплённые версии образов и инструментов, контейнеры и управляемые конфигурации. IaC описывает инфраструктуру декларативно или программно, позволяет ревью и повторение конфигурации. Но IaC само по себе не гарантирует полной идентичности среды, а одинаковая среда не гарантирует побайтово одинаковый результат сборки: временные метки, сеть и неконтролируемые входы могут различаться.

## 09:00–11:30. Воспроизводимые сборки

Термин Reproducible Builds в строгом смысле предполагает, что из одних исходников и идентичных параметров независимая сборка даёт побайтово одинаковый результат. Это отдельное свойство от совпадения тестовых стендов. Почему важно для безопасности? Если мы знаем исходники, а итоговый бинарный артефакт после пересборки отличается, возникает повод исследовать необъявленные входы или подмену. Однако даже побайтово идентичная сборка может содержать уязвимость в исходном коде. Поэтому повторяемость не заменяет моделирование угроз, анализ кода и тестирование. Для доказательства нужны хеши, сведения о происхождении, зафиксированные зависимости и процедуры независимой проверки.

## 11:30–14:00. Встраиваем DevSecOps

На проекте с ответственными данными TIMA добавляет в CI/CD несколько классов проверок. SAST анализирует исходный код. SCA анализирует сторонние компоненты и версии. Secret scanning ищет случайно раскрытые токены. Проверка IaC рассматривает небезопасные конфигурации. SBOM перечисляет программные компоненты, а provenance связывает конечный артефакт с источником и процедурой сборки. Каждая проверка должна иметь установленную область применения и ожидаемое поведение при ошибке. Если Trivy не смог загрузить базу CVE, нельзя сделать вывод «уязвимостей нет». Такая операция имеет статус BLOCKED или REVIEW_REQUIRED, исходя из политики. Отчёты необходимо сохранять, находки классифицировать и повторно проверять после исправлений.

## 14:00–17:00. Сквозной пример с GitHub Actions

Представим репозиторий Python API. При pull request запускаются форматирование, линтер, unit-тесты и проверка секрета; в отдельной задаче выполняется SCA. При слиянии в защищённую ветку создаётся артефакт, фиксируется SBOM и проверяются сведения о сборке. Затем приложение развёртывается на тестовый стенд. Интеграционные и отрицательные тесты проверяют, что без разрешения нельзя прочитать чужой документ. Результаты передаются на независимую оценку POLYGON. Перед production-release применяется правило утверждения риска человеком. У каждого шага есть идентификатор версии исходников, логи и критерии отказа. В этом смысл инженерного конвейера, а не просто в длинном списке инструментов.

## 17:00–20:00. Ошибки и ответ на интервью

Какие ошибки встречаются чаще всего? Первая — автоматически скачивать непроверенные версии библиотек. Вторая — давать CI runner избыточные токены. Третья — запускать непроверенный код pull request с производственными секретами. Четвёртая — не сохранять доказательства и не управлять ложными срабатываниями. Пятая — считать, что прохождение тестов равнозначно защищённости. На собеседовании скажите: «CI — регулярная интеграция изменений с автоматическими проверками. CD — доставка или развёртывание после заданных gate. Для повторяемости фиксируем версии, конфигурацию и окружения, используем IaC и происхождение артефактов. В DevSecOps встраиваем SAST, SCA, SBOM, проверку секретов и независимую квалификацию. Каждый сбой проверки фиксируется, а не превращается в ложный PASS». Помните: цель конвейера — ускорять контролируемые изменения, а не устранять ответственность инженера.

## Акценты для собеседования

1. **Сборочный конвейер:** Git commit запускает последовательность автоматических проверок и подготовки артефакта. Важно различать этапы, разрешения и критерии ошибок.
2. **CI и CD:** CI — непрерывная интеграция; Continuous Delivery — релиз готов к поставке, Continuous Deployment — автоматический выпуск после установленного gate.
3. **Воспроизводимость:** Похожие стенды ещё не гарантируют одинаковых артефактов: нужны закреплённые зависимости, toolchain, настройки, время и контроль источников.
4. **IaC:** Конфигурация среды описывается кодом, рецензируется и проходит тесты; изменение инфраструктуры становится отслеживаемым.
5. **DevSecOps в CI:** SAST, SCA, secret scanning, SBOM, подписи, provenance и независимые security gates добавляются по требованиям проекта.
6. **Пределы автоматизации:** Успешный pipeline не исключает ошибок требований, архитектуры, логики, полномочий или недостоверных результатов сканера.

## Практика TIMA

Спроектировать в GitHub Actions учебный workflow: checkout → закреплённые зависимости → unit tests → SAST/SCA → SBOM → тестовый deploy → human release gate. Определить поведение при сбое каждого этапа, доказательства и запрет секретов в непроверенных PR.
