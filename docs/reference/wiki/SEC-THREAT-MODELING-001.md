## Суть — 30 секунд

**Моделирование угроз:** структурированное исследование системы, её активов, взаимодействий, границ доверия и возможных негативных сценариев с целью заранее установить необходимые защитные меры и критерии проверки. Это не сканирование CVE: новая, ещё не написанная система может иметь серьёзные архитектурные угрозы.

**Основной принцип FATHER:** `IDEA+ (S0) → Security Requirements (S1) → S2 Threat Model → S3 Security Architecture → S4 Code → S5 POLYGON → S6 Release → S7 Monitor`. Риски и факты накапливаются в **едином реестре IDEA+**, без дублирования матриц.

**Важно:** STRIDE — метод классификации угроз, а не нормативный перечень обязательных контролей для любой системы. Обязательность российских актов зависит от вида системы, владельца, данных и действующей редакции. Без проверки текста конкретного пункта не приводить вымышленную нормативную цитату.

## Алгоритм THREAT-MODEL-v1: вход → обработка → выход

**Вход от S0/S1:** `IDEA_CONTRACT`, `SECURITY_PRECHECK`, `SECURITY_REQUIREMENTS`, описание процессов, видов информации, участников и предварительной архитектуры.

1. **Сформулировать задачи и границы:** что защищаем, какие функции, допущения и ограничения; что явно вне области анализа.
2. **Определить критичные активы:** информация, функции, ключи, учётные записи, API, сервисы, модели ИИ, журналы; связать с бизнес-процессами.
3. **Построить DFD:** внешние участники, процессы, хранилища, потоки, протоколы и привилегии; подписать **границы доверия**.
4. **Идентифицировать поверхность атаки:** для каждого потока/компонента найти точки входа, недоверенные источники и потенциально опасные операции.
5. **Проверить угрозы STRIDE:** Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege; не ограничиваться STRIDE, включить логику бизнеса и prompt injection для AI.
6. **Сформулировать сценарии:** `subject → preconditions → entrypoint → crossed_boundary → affected_asset → consequence`; неизвестные предпосылки явно отметить.
7. **Сопоставить факты:** MITRE CWE/CAPEC/ATT&CK, OWASP и БДУ ФСТЭК использовать в качестве гипотез и доказательств применимости, не как подтверждение реальной атаки.
8. **Передать в единый Risk Register (S2):** связать сценарии с `risk_id`, указать вероятность, последствия, методику, качество доказательств, неопределённость и владельца риска. Нет данных → `UNKNOWN`.
9. **Выбрать контролируемое решение (S3 + Cost):** предотвратить/снизить/избежать/передать либо предложить принятие риска; посчитать стоимость и архитектурные альтернативы; для существенного остаточного риска требуется решение уполномоченного человека.
10. **Создать тесты (S4/S5):** позитивные и отрицательные тесты, отсутствие обходов, воспроизводимое evidence, SHA-256 и независимая квалификация POLYGON.
11. **Запускать переоценку (S7):** при новой функции, зависимости, интеграции, изменении данных, CVE, инциденте, доступе AI-агента или изменении нормы.

**Выход:** `THREAT_MODEL.json`, `DFD`, `THREAT_SCENARIOS`, дополненные записи `risk_id`, `SECURITY_REQUIREMENTS_DELTA`, `SECURITY_DESIGN_REQUESTS`, `POLYGON_TEST_CASES`, `COST_IMPACT`.

## Шесть вопросов STRIDE на примере агента документов

| STRIDE | Контрольный вопрос | Пример для FATHER | Предлагаемый контроль |
|---|---|---|---|
| S — Spoofing | Можно ли выдать себя за другого субъекта? | Поддельная личность пользователя/сервиса | AuthN, проверка подлинности токенов |
| T — Tampering | Можно ли изменить данные или запрос? | Подмена документа/параметров команды агента | Целостность, валидация, контроль доверенных границ |
| R — Repudiation | Можно ли скрыть действия? | Агент записал файл без идентификатора операции | Аудит и причинно связанный trace_id |
| I — Information Disclosure | Можно ли прочесть чужое? | Агент получает чужие документы через общий индекс | Объектная авторизация, фильтрация RAG по допускам |
| D — Denial of Service | Можно ли остановить сервис? | Дорогие запросы или бесконечные циклы инструментов | Quotas, budget/time limits, circuit breakers |
| E — Elevation of Privilege | Можно ли расширить полномочия? | Prompt injection просит агента вызвать привилегированный инструмент | UAG tool policy, ограниченные права, подтверждение операций |

## ДФД — учебный пример (упрощение)

```text
[Пользователь] --(запрос)--> | Trust Boundary | --> [API/AuthN]
      [API/AuthN] --(principal + action)--> [FATHER UAG / Policy Decision]
      [UAG] --(разрешённое действие)--> [Agent Worker]
      [Agent Worker] --(ограниченный запрос)--> [Document Store]
      [Agent Worker] --(аудит без секретов)--> [Audit Store]
```

Наличие потоков на диаграмме не означает, что эти компоненты уже реализованы.

## Урок по возрастным уровням

- **Школьник:** рисует путь «я → приложение → база», находит места, где нельзя доверять чужому вводу; объясняет шесть карточек STRIDE простыми словами.
- **Студент:** рисует DFD и создаёт `THREAT_SCENARIOS` для примера API, придумывает проверки.
- **Junior:** реализует deny-by-default и объектную авторизацию; добавляет отрицательные тесты для IDOR и tampering.
- **Master:** моделирует сервисы, границы доверия, управление ключами, RAG-инъекции и обработку отказов.
- **Senior:** сравнивает архитектурные варианты, остаточные риски, стоимость, правовую применимость; утверждение риск-решения сохраняет за владельцем.

## POLYGON — минимальные критерии приёмки (не выполнены)

1. DFD включает всех известных участников, хранилища, потоки и границы доверия, есть scope и допущения.
2. Для всех критичных активов рассмотрены применимые сценарии и минимум шесть категорий STRIDE без искусственного требования «по одной угрозе каждой категории».
3. Для каждой существенной угрозы есть связь с `risk_id`, последствием, ответственным и выбранным/отложенным контролем.
4. Для каждого согласованного контроля есть способ проверки, негативный тест или обоснование ограничения метода.
5. Связи с источниками ведут на конкретный документ/раздел; для нормативных обязательных требований проверены редакция и применимость.
6. Доказательства сохранены; неизвестные значения не трактуются как отсутствие угроз.
7. Повторная экспертиза запускается при изменениях архитектуры; тестируемость подтверждена независимым POLYGON.
