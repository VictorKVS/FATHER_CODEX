## Короткая энциклопедическая справка

**CVSS (Common Vulnerability Scoring System)** — механизм оценки **серьёзности уязвимости**, формирующий балл 0.0–10.0 и машиночитаемый вектор исходных метрик. **CVSS Base Score не является оценкой риска организации**. Риск требует сценария, затронутого актива, вероятности/экспозиции, последствий, контроля и неопределённости. Одна и та же уязвимость с одинаковым Base Score может создавать существенно различный риск для двух систем.

**Официальный источник:** [FIRST CVSS v4.0 Specification Document](https://www.first.org/cvss/v4.0/specification-document), разделы *CVSS v4.0 Overview*, *CVSS Metric Groups*, *CVSS Scoring*, *Qualitative Severity Rating Scale*. Прямая короткая цитата из руководства FIRST: “CVSS Base (CVSS-B) scores are designed to measure the severity of a vulnerability” — [FIRST CVSS v4.0 User Guide](https://www.first.org/cvss/user-guide). Точный номер страницы HTML не фиксируется.

## CVSS v4.0 — четыре группы метрик

| Группа | Назначение |
|---|---|
| **Base (B)** | Внутренние характеристики уязвимости; оценка независимо от конкретной организации |
| **Threat (T)** | Изменяющаяся информация о наличии эксплуатации |
| **Environmental (E)** | Особенности целевой системы и значимость последствий |
| **Supplemental (S)** | Дополнительная характеристика для пользователя; сама по себе не изменяет расчётный CVSS-балл |

**Диапазоны качественной оценки FIRST/NVD для CVSS v3.x/v4.0:** None = 0.0; Low = 0.1–3.9; Medium = 4.0–6.9; High = 7.0–8.9; Critical = 9.0–10.0. [NVD Vulnerability Metrics](https://nvd.nist.gov/vuln-metrics/cvss). Нельзя использовать шкалу от версии 3.x для вектора v4.0; хранить `cvss_version` и полный `cvss_vector`.

**Важно:** CVSS v4.0 — не простое произведение вероятности и ущерба. Реализовать калькулятор «из головы» нельзя; для достоверного результата пользоваться [официальным калькулятором FIRST](https://www.first.org/cvss/calculator/v4.0) или проверенной эталонной реализацией и сохранять вектор и версию.

## Алгоритм FATHER CVE-TRIAGE v0.1

1. Получить от **реального сканера/SBOM** идентификатор уязвимости, конкретный компонент (purl/CPE), установленную версию, сведения о затронутом артефакте, время сканирования и версию vulnerability DB.
2. Проверить реальность компонента и попадание версии в affected range, **не** выводить наличие уязвимости из одного имени библиотеки.
3. Получить CVSS score **с версией и вектором** из проверяемого источника; при отсутствии честно записать UNKNOWN.
4. Установить, затрагивает ли уязвимость реально используемый код/входную точку, доступность эксплуатации, исправление, защитные меры; статус `NOT_ASSESSED` допустим.
5. Отдельно проверить [CISA KEV](https://www.cisa.gov/known-exploited-vulnerabilities-catalog) — наличие доказанной эксплуатации, и [FIRST EPSS](https://www.first.org/epss/) — статистический прогноз вероятности эксплуатации; **KEV ≠ EPSS ≠ CVSS**.
6. Привязать находку к `risk_id` **единого реестра IDEA+**; если риска нет — создать новую запись с происхождением данных. Определить последствия для бизнес-процесса, неизвестное, нормативную применимость.
7. Сформировать варианты обработки: исправление/миграция, временное ограничение, изоляция/компенсирующий контроль, вывод функции из эксплуатации, контролируемое принятие риска.
8. Cost Engineer сравнивает TCO, трудозатраты, последствия отказов и альтернативы; Security Architect предлагает ограничение; решение об остаточном существенном риске — уполномоченный человек.
9. POLYGON проверяет состояние после изменений: сканирование с актуальной DB, тесты, реальную конфигурацию, SBOM/хеши, регрессию; только затем возможен `QUALIFIED`.
10. При новых KEV/EPSS/CVE/SBOM событиях повторно оценить **затронутые** записи и сохранить историю.

**Принцип:** низкий CVSS не даёт автоматического разрешения на выпуск; высокий CVSS не является доказательством конкретного финансового ущерба.

```text
SCANNER FINDING + SBOM + VERSION

            ↓

```

## Российская нормативная ветка

**CVSS не является российским законом или универсальной заменой оценки угроз по методике ФСТЭК.** Для конкретного типа системы обязательность мер определяется отдельно:

- [ГОСТ Р 56939-2024 — Росстандарт](https://protect.gost.ru/gost/details/f3818925-a96f-4f55-96e9-46b44720ee64): методическая основа безопасной разработки ПО.
- [Методика оценки угроз безопасности информации ФСТЭК, 05.02.2021](https://www.consultant.ru/document/cons_doc_LAW_378330/): модели угроз и сценарии; URL на неофициальную правовую справочную систему, для юридического применения требуется официальная сверка.
- [БДУ ФСТЭК](https://bdu.fstec.ru/): источник сведений об угрозах и уязвимостях.
- [Российский нормативный справочник FATHER](../security-regulations.html) для проверки применимости 152-ФЗ, 187-ФЗ, приказов ФСТЭК и других документов.

**Точные пункты, обязательность и редакции** подбираются после определения вида системы (ИСПДн, ГИС, КИИ и т.д.). Без этого не утверждать, что CVSS требуется конкретным пунктом приказа.

## Практика по уровням и условия завершения

| Уровень | Задание | Критерий |
|---|---|---|
| Школьник | Найти разницу между оценкой уязвимости и риском для конкретного компьютера | Верно объясняет случай «уязвимость критическая, но компонент отсутствует» |
| Студент | Сохранить score, version, vector, component, evidence | Не подменяет CVSS вероятностью и учитывает неизвестные поля |
| Junior | Запустить SCA/Trivy на **своём разрешённом** тестовом артефакте, проверить SBOM и свежесть базы | Формирует воспроизводимый отчёт или честный BLOCKED |
| Master | Сопоставить CVSS, EPSS, KEV, экспозицию, меры и стоимость | Есть объяснимый план исправления/изоляции с допущениями |
| Senior | Подключить risk_id и контроль качества источников к SecGraph и POLYGON | Решение прослеживается от CVE до исправления и утверждения |

В предыдущей FATHER LAB-001 **Trivy CVE scan был BLOCKED из-за невозможности получить vulnerability DB**; полученный SBOM **не доказывает отсутствие CVE**. Нельзя подменять результаты реального сканирования учебным примером с вымышленным CVSS.
