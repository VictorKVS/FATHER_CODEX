# SEC-IDENTITY-001 — Идентификация, аутентификация и авторизация

## Короткий ответ (30 секунд)

- **Идентификация:** система узнаёт заявленный идентификатор субъекта (например, логин).
- **Аутентификация (AuthN):** проверяет подтверждение заявленной идентичности.
- **Авторизация (AuthZ):** определяет, разрешено ли **этому субъекту** выполнить **данное действие** над **данным объектом** при текущих условиях.
- **Правило:** успешная аутентификация **не** означает разрешение всех действий; неизвестный или недостаточный контекст → отказ по политике.

### Из книги: кто и что?

**Источник:** Phillip J. Windley, *Authorization in Action*, Manning MEAP Version 6 (2026), глава 1, §1.1, PDF с. 10, блок после «Accounts are where identity systems remember»: краткие формулы автора **“authentication determines ‘who,’ authorization determines ‘what.’”** (цитата до 10 слов). Автор объясняет, почему одной идентичности недостаточно при доступе к разным ресурсам.

**Проверка:** книга объясняет концепцию, но не устанавливает юридическую обязательность требований. Юридическую область действия определяем **отдельно**.

## Алгоритм: решение о запросе на чтение объекта

**Вход:** principal (субъект), credentials (доказательство), resource (объект), action (действие), context (контекст).  
**Результат:** ALLOW либо DENY + audit record.

1. Зарегистрировать идентификатор субъекта, не принимать его за доказательство подлинности.
2. Проверить безопасным механизмом подлинность субъекта и актуальность сессии/токена; ошибка → DENY.
3. Нормализовать идентификатор ресурса и требуемое действие; неизвестный объект/действие → DENY.
4. Получить **актуальные** права, атрибуты, отношения и ограничения (роль, назначение пациента и др.).
5. Оценить политику для `(principal, action, resource, context)`; отсутствие явного разрешения → DENY.
6. Применить решение **на сервере** до обращения к данным; запретить обход проверки альтернативным endpoint.
7. Записать audit event (идентификатор операции, решение, reason code), **без паролей и токенов**.
8. При изменении прав заново проверять применимость решения; задокументировать TTL/отзыв.

**Учебный псевдокод (не реализация промышленной IAM):**
```python
def authorize(authenticated: bool, permissions: set[str],
              owner_id: str, actor_id: str) -> bool:
    if not authenticated:
        return False
    return "record:read" in permissions and owner_id == actor_id
```

**Ограничения:** сравнение владельца не заменяет реальную модель врач–пациент и не даёт прав на лечение; RBAC, ABAC и ReBAC могут комбинироваться. Отдельно нужны угрозы обхода, отзыва токенов, IDOR и fail-closed.

## Объяснение по уровню

- **Школьник:** пропуск в школу доказывает, кто ты, но не даёт ключ от кабинета директора.
- **Студент:** один endpoint, два пользователя, 200 для разрешённого объекта и 403 для запрещённого.
- **Junior:** реализовать middleware/проверку доступа, negative tests и журналирование без секретов.
- **Master:** сравнить RBAC/ABAC/ReBAC и точку проверки политики, найти IDOR и расхождения в правах.
- **Senior:** документировать policy decision/enforcement, обоснование отказа, отзыв, надежность, аудит, privacy и риски делегирования AI-агентам.
